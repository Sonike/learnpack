# Expense tracker with SQLite

Build a command-line expense tracker backed by SQLite, in its own GitHub repository. It's small enough to finish in a week of evenings, and it exercises everything in this section: schema design, constraints, joins, grouping, transactions, indexes and safe SQL from Python. It's also a good interview project: "walk me through your schema" and "how do you stop SQL injection?" are questions you'll be able to answer with your own code on screen.

## What you're building

A CLI where someone can record what they spend, organise it into categories, set monthly budgets, and see reports.

```bash
python -m expenses add --amount 4500 --category food --date 2026-03-02 --note "lunch with team"
python -m expenses report month 2026-03
python -m expenses report budget 2026-03
```

```
March 2026
food        ₦ 41,300   budget ₦ 50,000   83%
transport   ₦ 18,900   budget ₦ 15,000  126%  over by ₦ 3,900
rent        ₦150,000   budget ₦150,000  100%
total       ₦210,200
```

The exact commands and output format are yours to design. Use `argparse` (from *Errors, debugging, files and modules*) for the CLI.

## Requirements

### 1. Schema

At least three tables: `users`, `categories` and `expenses`, plus `budgets` if you build the budget report.

- Every table has an `INTEGER PRIMARY KEY`.
- Foreign keys link expenses to a user and a category, with `PRAGMA foreign_keys = ON` set on every connection.
- Constraints do real work: `NOT NULL` where a value is required, `CHECK (amount > 0)`, `UNIQUE` category names per user, dates stored as `'YYYY-MM-DD'` text.
- Store money as whole numbers of the smallest unit (kobo or cents), never as floats. `0.1 + 0.2` is not `0.3` in floating point, and money must add up exactly.

Draw the schema as an ASCII diagram in your README, like the ones in *Relationships and joins*.

### 2. A repository layer

All SQL lives in one module (for example `expenses/repository.py`). The CLI calls methods like `add_expense(...)`, `monthly_totals(month)` and `budget_vs_actual(month)` and gets back dataclasses or plain dicts, never cursors.

- Every value goes through `?` parameters. No f-strings, `+` or `%` in SQL.
- Write a test that stores a note like `'); DROP TABLE expenses;--` and proves it comes back unchanged and the table survives.

### 3. Reports

At least three reports, each one SQL query:

- **Monthly totals:** total spent per month (`substr(date, 1, 7)` gives `'2026-03'`).
- **Top categories:** the top 5 categories by spending for a month, with a `GROUP BY` and `JOIN`.
- **Budget vs actual:** each category's budget beside what was spent, including categories with a budget and **no** spending (a `LEFT JOIN`, with `COALESCE(SUM(amount), 0)` turning a `NULL` sum into 0).

### 4. One index, justified

Pick the query your app runs most (probably "expenses for this user in this month"). In the README, paste the `EXPLAIN QUERY PLAN` output **before** and **after** adding an index, and explain in two sentences why you chose those columns.

### 5. One atomic operation

Pick one:

- **Move budget** between two categories: subtract from one, add to the other, all or nothing.
- **Bulk import** a CSV of expenses: if any row is invalid (an unknown category, a negative amount), none of the rows are saved.

Write a test that makes it fail halfway and asserts nothing changed.

### 6. Tests

Integration tests that run your repository against `sqlite3.connect(":memory:")`, so each test starts with a clean database. Cover the reports with small, hand-checked data (you should be able to work out every expected number on paper), the constraints (bad data is refused), and the atomic operation. Run them with `pytest`.

## Suggested steps

1. Write the schema in a `schema.sql` file and load it with `conn.executescript(...)`. Insert some rows by hand in the `sqlite3` CLI and try your report queries there first.
2. Build the repository one method at a time, test first.
3. Add the CLI last, as a thin layer that parses arguments and prints what the repository returns.
4. Add the index and the README.

## Using AI on this project

Ask an AI assistant to explain an error, review your schema, or suggest edge cases for your tests. Write the queries and the code yourself: being able to explain each one, line by line, is the point of the project.

## Stretch goals

- A `users` login flow is out of scope, but support several users with `--user` and make sure reports never mix their data (a test proves it).
- Export a month to CSV with the `csv` module.
- Recurring expenses (rent every month) generated by a command.
